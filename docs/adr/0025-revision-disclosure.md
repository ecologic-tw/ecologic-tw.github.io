# ADR-0025 內容修訂的揭露方式

- 日期：2026-09-27
- 狀態：提議（待決定事項已由 Decision Owner 於 2026-09-27 決定，見文末；接受後由 Decision Owner 更新狀態）
- Decision Owner：@Wang-Yi-Zhang
- Review Point：第一則附 `about` 的勘誤說明上線後，檢查內容頁、`/updates/` 與訂閱源是否一致；與 ADR-0024 一起在半年後依回饋表單意見檢視分級是否合用

## 背景
ADR-0024 已提供 `/updates/`、Atom 訂閱源與手寫說明（`kind: content／fix`），但修訂仍不容易被讀者發現：

- 修改 `updated` 不會產生任何公告；`updated` 連錯字修正也會變動，不能當作「實質修訂日期」。
- 圖鑑卡與情境題頁沒有修訂紀錄，讀者無法得知先前讀到的說明或正解是否已改。
- 手寫說明只有站內 `link`，沒有對應的內容 id，內容頁無法反查自己的修訂。
- 進度只以題目 id 保存 `correct` 與 `at`（`src/lib/progress.ts`）。正解改變後，題目列表仍依舊紀錄顯示「答對」（`src/scripts/practice-status.ts`）。
- 內容退回草稿後，正式網站不再產生該頁，本站也沒有自訂 404 頁。`/updates/` 頁上的連結已由產物的站內連結檢查確認目標存在（Issue #41），但手寫說明若連到被撤下的頁面，建置就會失敗。
- 匯入進度時，`parseImport` 會丟掉目前站上沒有的 id；內容暫時撤下期間匯出再匯入，該項紀錄就會遺失。
- 已有實例：cons-013 於 PR #27 發布、PR #35 退回修正機率推論的說明、PR #40 重新發布；不當訴諸權威於 PR #46 補充實踐權威的界線。架構審查也提過「題目已更新」提示的需求（`docs/review/2026-09-27-architecture-audit.md`）。

## 決策
1. **依是否改變內容意義分四級揭露**：

   | 級別 | 例子 | 揭露方式 |
   |---|---|---|
   | 細微 | 錯字、排版、不影響意思的潤飾 | 只改 `updated`，保留 Git 紀錄，不寫說明 |
   | 補充 | 補例子、來源、適用條件 | `kind: content`，附 `about` |
   | 勘誤 | 定義、推論、正解或重要事實修正 | `kind: fix`，附 `about` 與 `impact` |
   | 撤下 | 退回草稿重新審核 | `kind: notice`，附 `about`，不附 `link` |

   判斷有疑義時，由內容審核者決定，寧可往上一級揭露。

2. **只用一份資料**：沿用 `src/content/updates/zh-TW/updates.yaml`，不另建修訂紀錄檔。說明新增兩個選填欄位：
   - `about`：對應內容，格式為 `entry/<id>`、`scenario/<id>` 或 `term/<id>`；只用於 `content`、`fix`、`notice`。
   - `impact`：對學習的影響，`none`（不影響先前理解）／`reread`（建議重新閱讀）／`answer-changed`（正解改變）。必須搭配 `about`；`answer-changed` 只用於 `fix`，且對象須為情境題或有小檢核的圖鑑卡。

   說明的 `summary` 寫清楚改了什麼、為什麼改；日期用 `date`。凡是有 `about` 的說明都列入 `/updates/` 與訂閱源（影響一併列出），不再細分「只在內容頁顯示」。

3. **修訂說明跟著內容的審核狀態**：`content`、`fix` 說明只在 `about` 指向的內容已發布時列出，並在沒有 `link` 時自動連到該內容頁。內容尚未通過審核時，說明不顯示，`npm run check` 發出警告。撤下公告一律列出，不連到內容頁。

4. **內容頁顯示修訂**（第一階段：圖鑑卡與情境題；名詞只列在 `/updates/`）：
   - 標題下方顯示「最近修訂：YYYY-MM-DD（補充／勘誤）」，資料來自最新一則 `about` 指向本頁的 `content` 或 `fix` 說明，不使用 `updated`。
   - 以 `<details>` 列出歷次修訂說明（含撤下公告），新到舊，舊紀錄不刪除。圖鑑卡放在參考資料之後。情境題的修訂說明可能提到答案，所以放在作答後才出現的解說區塊內，標題下的日期也不加連結。
   - 沒有修訂說明的頁面不顯示這兩個區塊。

5. **正解改變的提示**：
   - `impact: answer-changed` 的情境題，在題幹前顯示中性提示「本題答案已於 YYYY-MM-DD 修正，說明見解說」；圖鑑卡則在小檢核題目前提示。不提前透露答案，提示為靜態 HTML。
   - 題目列表中，作答日期（`at` 的 UTC 日期）不晚於修正日期的紀錄，改顯示「已作答（題目後來修正過）」，不顯示「答對」。部署時間不固定，修正當天的作答也算在修正前：寧可少顯示一次「答對」，也不把舊正解下的結果當成答對。只在本機比對，不上傳。
   - 不修改、不刪除既有作答紀錄、收藏與徽章，不因網站修錯而收回使用者已得到的東西。

6. **撤下期間的進度**：有撤下公告且目前未發布的內容，其 id 提供給 `/me/`，匯入進度時視為認得的 id，紀錄予以保留；重新發布後即可接回。畫面與徽章仍只依已發布內容計算。

7. **審核與上線**：附 `about` 的說明必須和它描述的內容修訂放在同一個 PR，由同一位內容審核者一起確認後才合併；說明本身不另設 `status`。AI 起草的說明要在 PR 中標明。`published` 維持首次發布日期（ADR-0024），修訂日期以說明的 `date` 為準。

8. **第一批說明**：補寫 cons-013（`fix`，`impact: reread`，正解未變）與不當訴諸權威（`content`，`impact: reread`）兩則修訂說明。

## 依據的資訊與假設
- 假設讀者關心的是「這次修改是否影響我先前的理解」，而不是每一次改動。按意義區分主要／次要修改，與 GOV.UK 等公共資訊網站的變更說明做法相近（參考資料待 Decision Owner 確認）。
- 修訂量不大，實質修訂全數進訂閱源不會造成干擾。
- 靜態 HTML 與既有本機腳本即可完成，不需後端、金鑰或追蹤，不影響 CSP。撤下內容的 id 本來就出現在公開的撤下公告中，放進 `/me/` 頁不多揭露任何資訊。

## 已知風險
- **維護者漏寫說明**：內容頁不會顯示修訂，讀者看不出改動。緩解：審核指南加入分級，PR 範本加入檢查項。程式無法判斷一次修改是否「改變意義」，只能靠人工。
- **說明本身沒有 `status` 審核門檻**：改以「同一個 PR、同一位審核者」把關，程式無法驗證這條規則。修訂說明跟著內容的審核狀態顯示，至少不會出現「內容還沒審、勘誤先上線」。若日後發生說明未經審核就上線的情況，改為給說明加 `status`。
- **撤下期間只有匯入受保護**：未寫撤下公告就退回草稿的內容，匯入時仍會遺失紀錄。`localStorage` 本身不受影響。
- **同日作答的誤判**：修正當天、修正上線後才作答答對的人，也會看到「已作答（題目後來修正過）」，重新作答後恢復正常顯示。
- **提示文字造成焦慮或被誤解為催促**：文案沿用 ADR-0024 的邀請語氣，不使用「重要！」「請立即重做」等字眼，不用警示色。

## 考慮過的選項（含不同意見）
- **以 `updated` 或 Git 歷史自動產生修訂紀錄**：錯字與實質修訂無法區分，也需要建置環境保有完整 Git 歷史，不採用。
- **每筆內容自帶 `revisions` 欄位**：資料靠近內容，但與 `updates.yaml` 重複，兩份文字容易不同步，不採用。
- **補充級只在內容頁顯示、不進訂閱源**：需要多一個旗標，第一階段不值得。修訂量變大時再評估。
- **只對修正前已作答者顯示答案修正提示**：要依賴腳本；未作答的新讀者看到提示也無害，所以題幹提示維持靜態，只有題目列表依本機紀錄調整。
- **給說明加 `status`／`reviewers`**：可沿用內容的審核門檻，但每則說明都要多一次標記，且 `npm run review` 需要支援 YAML 陣列。Decision Owner 決定先用同 PR 規則。
- **`content`／`fix` 說明必須指向已發布內容，否則檢查失敗**：內容退回草稿時會迫使刪除舊說明，違反「舊紀錄保留」，改為跟著內容狀態顯示。

## Decision Owner 的決定（2026-09-27）
1. 說明不另設 `status`，以「同一個 PR、同一位審核者」為準。
2. 補寫 cons-013 與不當訴諸權威的修訂為第一批說明。
3. 撤下期間匯入遺失紀錄的問題在本階段一併處理（決策第 6 點）。
