# ADR-0036 多方觀點情境：`cases` 集合

- 日期：2026-09-29
- 狀態：接受（2026-09-29，@Wang-Yi-Zhang）
- Decision Owner：@Wang-Yi-Zhang
- Review Point：1 則試行案例完成雙人審核並有至少一位試讀者回饋後，檢視：讀者是否先讀角色卡再作答、各角色是否讓人覺得公平、共同點與提問兩題的正解是否唯一、審核負擔能否承受；再決定擴充、修訂或停止

## 背景
[SDD 13](../sdd/13-interaction-roadmap.md) §6 規劃「多方觀點情境」：一個虛構議題、3–4 個角色，練習找共同點、找出真正的分歧點。它排在第 4 項，前置條件是爭點地圖上線並試讀，以及有第二位審核者。

目前的狀態：
- 爭點地圖（[ADR-0034](0034-issue-map-classify.md)）已上線，2 題試行題已發布（PR #87），**還沒有試讀回饋**。
- **還沒有第二位審核者**（見 `docs/handoff.md`），這也是 M5 的主要卡點。
- 現有題目都是單頁單題；圖鑑、進度、徽章都以單一情境題為單位。

SDD 13 §6 原本建議小題 1「大家都同意什麼？」用 `multi`。盤點後發現行不通：`multi` 的選項是圖鑑卡 id（[ADR-0022](0022-advanced-question-formats.md)），不能放「兩位角色都同意水質要改善」這種自訂句子。

## 決策
1. **新增內容集合 `cases`**（`src/content/cases/zh-TW/*.md`）。一個案例包含議題背景與 3–4 張角色卡；小題仍是一般情境題，以 `case` 欄位連到案例。
2. **案例資料格式**（實作時寫入 03）：
   ```yaml
   id: daily-case-01            # (daily|cons)-case-\d{2}，前綴與 theme 一致
   theme: daily
   title: 社區要不要設共享廚房
   summary: 三戶人家對同一個空間有不同的打算。   # 80 字內，列表用
   roles:                       # 3–4 個
     - id: resident-a           # 案例內不重複
       name: 阿美（一樓住戶）      # 虛構，不對應可辨識的真實團體、機關或個人
       cares: ……                # 在意什麼（必填）
       grounds: ……              # 手上有什麼依據（必填；可以是經驗，事實性依據附來源）
       worries: ……              # 擔心什麼（必填）
       misread: ……              # 容易被誤解的地方（必填）
   # 共用審核欄位（sources、reviewers、status、requiresSecondReview……）
   ```
   本文分兩段：`## 背景`（議題背景）與 `## 換個位置想`（全部小題答完後的收尾，規則同 [ADR-0029](0029-perspective-section-and-charity-card.md)）。
3. **小題**：每個案例 2–3 題，都是一般情境題，加上選填欄位 `case: <案例 id>`。建議組合：
   1. **共同點**：`choice`，新任務 `common-ground`，題目上方顯示「找出共同點」：哪一項是所有角色都會同意的？
   2. **分歧在哪**：`classify`（沿用 ADR-0034）。
   3. **先問什麼**：`choice`，新任務 `ask-first`，題目上方顯示「先問什麼」：想更了解某一位角色，最好先問哪一句？
   - 不新增題型，只在 `CHOICE_TASKS` 加兩個任務值。
   - 小題依 id 排序，這就是案例內的作答順序。
4. **模式**：第一版的小題都是 `difficulty: advanced`。`choice` 本來就只出現在進階模式（ADR-0022 §2）；同一案例內的小題難度要一致。基礎模式的主題完成徽章不受影響。
5. **頁面**：
   - `/cases/`：案例列表，依主題分組。練習頁（`/practice/[theme]/`）加一個入口。
   - `/cases/[id]/`：背景、角色卡（每張是 `<details>`，手機可以逐張展開）、小題清單與作答狀態、收尾的「換個位置想」與[討論引導卡](0033-discussion-card.md)連結。
   - 小題頁沿用 `/scenario/[id]/`。題目上方顯示「多方觀點：〈案例名〉第 n／N 題」，角色卡摘要收在可展開區塊，讀者從隨機一題或題目列表直接進來時也能作答。
   - 小題的「下一題」連到同案例的下一題；最後一題連回案例頁的收尾。
   - 小題照常出現在題目列表，並標出案例名稱；**隨機一題不抽案例小題**，因為沒讀過背景時負擔太大。綜合挑戰只抽 `judge` 題，不受影響。
   - 沒有 JavaScript 時：背景、角色卡、小題清單都能閱讀；作答狀態需要 JavaScript，沒有時不顯示。
6. **進度**：沿用 `answered`，不新增欄位，進度版本維持 1。「案例完成」由全部小題都有作答紀錄推導，只顯示在案例頁；第一版不發徽章。
7. **點亮圖鑑**：依各題型原本的規則（`choice` 不點亮、`classify` 點亮「分歧的種類」），案例本身不點亮卡片。
8. **建置期檢查**：
   - 案例有 3–4 個角色，id 不重複；每個案例有 2–3 題小題，`case` 指向存在的案例，且主題一致。
   - **發布一致**：已審的小題所屬案例也必須已審；已審的案例至少要有 2 題已審小題。避免出現缺背景的小題，或沒有題目的案例。
   - 保育案例與其小題必須 `requiresSecondReview: true`；同一案例的小題與案例本身的 `requiresSecondReview` 要一致（見第 10 點）。
   - 角色卡文字與背景套用既有的網址、電話、Email 檢查與粗體檢查。
9. **寫作規則**（補充 08）：
   - 不設計「正確的一方」：每個角色都有合理的關切，也至少有一個容易被誤解的地方。
   - 理解不等於同意，溫柔不等於放棄事實：某個角色的事實主張若證據較弱，可以在背景或解說中說明並附來源，不必為了平衡而假裝各方證據一樣強。
   - `common-ground` 的干擾選項是「只有部分角色同意」或「把某個角色的主張誇大成大家都同意」；正解必須在每張角色卡都找得到依據。
   - `ask-first` 的正解是開放、針對該角色關切的問題；干擾選項優先用：誘導式問題、推測動機或人格、只問是非、與該角色的關切無關。
   - 題目不問讀者自己同意哪一方。
10. **審核**：
    - **保育案例**一律 `requiresSecondReview: true`。第二位審核者到位前，可以先做程式與草稿，但**不能發布**。
    - **日常案例**依 08 判斷：涉及仍有社會爭議的議題才標 `requiresSecondReview: true`。是否屬於爭議議題由 Decision Owner 判斷，並寫在該案例的 PR 說明（同 ADR-0031 的 cons-021）。
    - 這是 SDD 13 §6「一律雙審」的例外。
11. **比例與平衡**：案例小題沒有「犯錯的一方」，不計入保育題立場平衡的「由保育方犯錯」，但計入對照題比例的分母（同 ADR-0031、ADR-0034）。
12. **分階段實作，各自開 PR**：
    1. schema、建置期檢查、內容索引、單元測試；同步更新 03、CONTEXT。
    2. 案例頁、小題頁的案例標示與導覽、e2e 與淺色／深色 axe；同步更新 04、06。
    3. 1 則試行案例草稿（3 個角色、3 題小題），`draft`、`aiAssisted: true`。
13. **工具**：`npm run scenario -- new` 可指定 `--case` 與兩個新任務。案例本身第一版直接以 draft 撰寫，不做提案工具；有外部投稿需求時再議。

## 依據的資訊與假設
- 已確認：`multi` 的選項是圖鑑卡 id，不能裝自訂句子（`src/lib/content-schema.ts` 的 `multiScenario`）。
- 已確認：`choice` 每題 3–4 個選項、恰好一個正解、每個選項附解說，改任務值不必改作答元件（ADR-0031 的做法）。
- 已確認：情境題頁的題型元件已拆開（`docs/sdd/06` 的「情境題頁面與題型元件」），小題沿用既有頁面，只要加案例標示與導覽。
- 假設 1：讀過角色卡再作答，比單題更能練習「先理解，再回應」。
- 假設 2：3 題小題的閱讀量在進階讀者可承受的範圍內；閱讀篇幅報告照常提醒。
- 假設 3：小題頁附上角色卡摘要，足以讓直接進入的讀者作答。

## 已知風險
- **保育案例卡在第二位審核者**：會跟 M5 一樣等人。若到 Review Point 仍沒有第二位審核者，保育案例暫停，不放寬雙審。
- **日常案例只有一位審核者**：多角色案例的重點是立場平衡，單人審核較容易漏看偏向。緩解方式：只有 Decision Owner 判斷不屬爭議議題時才能單審；試讀時特別詢問各角色是否公平；有疑慮就改標雙審。
- **試讀只能看草稿**：目前沒有公開的草稿預覽，試讀者需要本機執行 `npm run dev`，或由維護者陪同操作。
- **「共同點」與「先問什麼」的正解不唯一**：好的問題可能不只一個。緩解方式：干擾選項各有明確缺陷（第 9 點）；試讀時特別檢查。一題若有兩個同樣合理的答案，改寫選項或刪題。
- **角色對應到真實團體**：即使虛構，讀者仍可能聯想到特定團體。緩解方式：不用真實地名與團體名稱，角色以身分與關切描述；雙審時特別檢查。
- **變成「各說各話都一樣好」**：違反 SDD 13 共同原則 1。緩解方式：第 9 點的寫作規則；解說分清楚哪些分歧能靠資料解決。
- **對照題比例被稀釋**：每個案例會加 2–3 題非對照題。已發布集合的比例照常由建置期檢查把關。
- **案例與小題不同步**：例如小題已審、案例還是草稿。第 8 點的發布一致檢查處理。

## 考慮過的選項
- **照 SDD 13 用 `multi` 問共同點**：`multi` 的選項是圖鑑卡，裝不下自訂句子；要擴充就是新題型，工作量與審核量都變大。改為 `choice` 單選，若試讀顯示「只能選一個」太受限，再考慮新增自訂句子的多選題型。
- **整個案例做成一頁、多個表單**：讀者不必換頁，但作答腳本、結果區、改寫練習都要改成多題；沿用情境題頁的成本低很多。
- **案例列出 `questions` 清單，而不是小題寫 `case`**：順序可以明寫，但小題檔看不出自己屬於哪個案例，小題頁也要反查；照 SDD 13 由小題指向案例，順序用 id。
- **小題不出現在題目列表**：案例更完整，但小題本身仍是可以獨立作答的題目，藏起來會讓讀者找不到；改為在列表標出案例名稱，只排除隨機一題。
- **案例一律雙審**（SDD 13 §6 原案）：立場平衡最有保障，但第二位審核者到位前完全不能發布，也拿不到試讀回饋。Decision Owner 決定日常案例依 08 判斷，保育案例維持雙審。
- **基礎模式也可以出現**：`classify` 有這個例外（ADR-0034），但 `choice` 仍限進階，而且案例的閱讀量較大；先放進階，試讀後再議。

## 後果
- 新增一個內容集合、兩個頁面、兩個 `choice` 任務值；情境題 schema 多一個選填欄位 `case`，既有題目不受影響。
- 03、04、06、08、CONTEXT（「多方觀點情境」`case`、「角色卡」`role`）與投稿指南在實作 PR 中同步更新。
- 需要以下測試：
  - 單元測試：案例 schema（角色數、id 不重複）、`case` 參照與主題一致、發布一致、小題數、雙審要求。
  - e2e：從案例頁走完一個案例、小題頁的案例標示與下一題、隨機一題不抽案例小題、沒有 JavaScript 時可讀、淺色與深色 axe、手機排版（角色卡可展開）。
- 保育案例的發布要等第二位審核者；日常案例不屬爭議議題時可以單審發布。
