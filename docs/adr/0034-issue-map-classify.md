# ADR-0034 爭點地圖：`classify` 題型

- 日期：2026-09-29
- 狀態：提議
- Decision Owner：@Wang-Yi-Zhang
- Review Point：2 題試行題完成人工審核並有至少一位試讀者回饋後，檢視：逐句分類是否有第二種合理答案、「可接受」的用法是否清楚、基礎模式讀者是否覺得太難；再決定擴充、修訂或停止

## 背景
[SDD 13](../sdd/13-interaction-roadmap.md) §5 規劃「爭點地圖」。許多衝突其實混著不同種類的分歧，學會分類，就知道哪些爭論查資料就能解決，哪些需要協商。前置條件「分歧的種類」概念卡（`kinds-of-disagreement`）已於 2026-09-29 發布（PR #81），它是後續「多方觀點情境」（SDD 13 §6）的基礎。

現有題型（ADR-0022）的答案單位都是「整段推理」，沒有「逐句判斷」的題型。

## 決策
1. **新增 `format: classify`**：一段虛構對話，加上 3–5 句從對話摘出的爭點，每句從四種分歧中選一種：事實、價值、定義、利益。
2. **資料格式**（實作時寫入 03）：
   ```yaml
   format: classify
   prompt: 下面每一句，比較像哪一種分歧？   # 選填，預設用這句
   items:                                   # 3–5 句
     - id: parking-count                    # 同題內不重複
       text: 「停車場蓋好後，每天會多三百輛車開進來。」
       answer: fact                          # fact | value | definition | interest
       acceptable: []                        # 選填 0–1 個：界線模糊時也算對的類型，不可與 answer 相同
       note: 可以用交通調查或類似地點的資料檢驗……   # 每句必填
   ```
   - 四種類型是固定的常數，放在程式裡，內容檔不另外列出。之後要擴充類型時另寫 ADR。
   - `betterPhrasing`、`checklist` 選填，與 `choice` 相同。
   - `items` 的文字與 `note` 套用既有的網址、電話、Email 檢查與粗體檢查。
3. **判定**（純函式，放在 `src/lib/quiz.ts`）：
   - 每一句都要選才能送出。
   - 每句選到 `answer` 標 ✓ 正解，選到 `acceptable` 標 △ 可接受，其他標 ✗，並顯示正解與該句的 `note`。圖示一律搭配文字。
   - **每一句都是正解或可接受，才算答對**；不計分，也不顯示部分得分。整體結果沿用「判讀正確」「換個角度看看」。
4. **模式**：`classify` 依 `difficulty` 決定出現在哪個模式，**基礎與進階都可以**。這是 ADR-0022 §2「新題型只出現在進階模式」的例外：逐句分類是理解分歧的基本功，也是之後多方觀點情境的基礎。
   - 基礎模式的主題完成徽章（只看 basic 題）會納入 basic 的 `classify` 題。已得到的徽章不會收回（只增不減）。
5. **點亮圖鑑**：`classify` 題答對時點亮「分歧的種類」卡。建置期檢查這張卡存在；已審的 `classify` 題要求它也已審。
6. **比例與平衡**：
   - `classify` 題沒有「犯錯的一方」，不計入保育題立場平衡的「由保育方犯錯」，但計入對照題比例的分母（與 ADR-0031 鋼人題相同）。
   - 保育主題的 `classify` 題若涉及 08 所列的爭議議題，照常標 `requiresSecondReview: true`。
7. **不問讀者自己的立場**：題目只問「這句話屬於哪一種分歧」，不問讀者同意哪一方。
8. **不進綜合挑戰**：綜合挑戰（ADR-0032）只抽 `judge` 題，本題型不影響它。
9. **試行內容**：先起草 2 題（日常 1、保育 1），皆 `draft`、`aiAssisted: true`。
10. **工具**：`npm run scenario -- new --format classify` 產生提案範本；內容品質報告與審核工具支援新題型。

## 依據的資訊與假設
- 假設：逐句分類比整段判讀更能讓讀者看出「同一場爭論裡有不同種類的分歧」。
- 四分類沿用「分歧的種類」卡，那張卡已寫明這是教學用的簡化分類。

## 已知風險
- **分類本身有爭議**，例如定義與價值的界線模糊：用 `acceptable` 與逐句解說寫明理由；試讀時記錄讀者的分歧。一句話若有兩種以上同樣合理的答案，就改寫或刪掉那一句，不靠 `acceptable` 硬撐。
- **變成政治立場測驗**：情境虛構、立場平衡，只問分歧種類，不問讀者立場。
- **基礎模式太難**：先放 1 題在基礎模式試行，依 Review Point 調整。
- **題目數量增加稀釋對照題比例**：分母包含 `classify` 題，建置期檢查照常把關已發布集合的比例。

## 考慮過的選項
- **只放進階模式**：符合 ADR-0022 §2，但逐句分類比多重判讀、有效×健全簡單，放在進階會讓基礎讀者錯過；SDD 13 也建議兩種模式皆可。Decision Owner 可在接受時改為只放進階。
- **把類型列在每題的 `categories` 欄位**：可以每題不同，但目前只有四類，放在內容檔會重複，也容易打錯；改為程式常數。
- **允許多個 `acceptable`**：彈性較大，但「幾乎都對」會讓題目失去練習價值；限制為 0–1 個。
- **答對不點亮任何卡**：與 `choice` 題一致，但這個題型本身就是在練習「分歧的種類」，點亮那張卡更合理。

## 後果
- 情境題 schema 多一個題型，作答頁多一種作答元件。
- 判定純函式、內容檢查、提案工具、內容品質報告都要支援新題型。
- 需要以下測試：
  - 單元測試：schema 規則（句數、id 不重複、`acceptable` 不等於 `answer`）、判定、點亮。
  - e2e：作答、逐句標示、沒有 JavaScript 時可讀、淺色與深色 axe。
