# 10 治理、審核與傳承

社群文化與原則以 [`docs/共好型自主敏捷社群指引.md`](../共好型自主敏捷社群指引.md) 為準；本章定義具體的角色、流程與交接做法。

## 角色（角色，不是職位）
| 角色 | 職責 | GitHub 權限 | 人數 |
|---|---|---|---|
| 管理員（Owner） | Org 設定、成員權限、外部資產保管 | Org Owner | ≥ 2（避免單點失效） |
| 維護者 | 核准 PR、維護紅線與品質 | repo write、CODEOWNERS | ≥ 1 |
| 內容審核者 | 審核邏輯正確性／保育事實；保育爭議題需第二位 | triage 以上 | 不限 |
| 回饋整理者 | 整理表單回應、轉開 Issue、去除個資 | 表單協作者 | ≥ 1 |
| 決策者 | 個別重大決策的推進與紀錄（每次指定） | — | 每案 1 |
| 行為準則聯絡人 | 受理 D 類回報（指引 §15） | — | ≥ 1，另設外部觀察員 1 |
| 貢獻者 | fork＋PR、開 Issue、投稿 | — | 不限 |

## 角色檢視與輪替（每半年，3 月與 9 月）
1. 以 Issue 範本「角色檢視」開單，公開至少 14 天。
2. 回答指引 §24 的五個問題，列出本期重大決策（ADR 清單）。
3. 每個角色決定：續任／交接／分享（增加一人）。**同一人連續承擔同一角色滿 2 年，下一期優先交接或分享**；無人接手時可續任，但須在紀錄中寫明。
4. 更新角色名冊與 CODEOWNERS。
即使只有一位維護者，也照常開單、自我檢視並公開紀錄。

## 決策方式
見指引 §8 對照表。重點：
- 內容由提案者決定寫法；審核閘門只檢查紅線與品質。
- 架構、依賴、流程變更 → ADR，指定決策者，填寫假設、已知風險、回顧點。
- 紅線、授權、指引等社群基本規則 → ADR＋公告 Issue，公開徵詢至少 14 天。

## 內容生命週期
`draft` →（PR＋審核檢核表＋≥1 維護者核准，reviewers 填入）→ `reviewed` →（過時或有誤）→ `retired`
- `retired` 不發布但保留檔案；情境題網址導向主題列表並說明已下架。
- 已上線內容被回報判讀錯誤 → 先修正或下架，再以學習回顧檢討審核機制（不追究審核者個人）。
- 所有內容變更走 PR，禁止直接 push `main`。

內容 schema 與人工標記工具依 ADR-0017 檢查來源與不同審核帳號數；`requiresSecondReview: true` 至少兩人。對照題雙審開關目前關閉（只有一位維護者），啟用方式見審核指南。帳號欄位不能證明實際人工審核，PR 核准仍須由人類完成。

## 學習回顧
觸發：已上線內容錯誤、內容指涉真實人事物、網站異常、資安事件（修復後、去識別化）。使用 Issue 範本 `learning-review.yml`，依指引 §16 九個問題進行。

## 傳承機制
1. **文件即交接**：`AGENTS.md`（共用 AI 規範）＋`CLAUDE.md`（導讀入口）＋`docs/sdd/`＋`docs/adr/`＋指引須與程式同步；跨 AI 工具接手依 `AGENTS.md` 的交接流程，開工提示見 `CONTRIBUTING.md`。
2. **外部資產清單**（交接時逐項移轉）：
   | 資產 | 持有者 | 交接方式 |
   |---|---|---|
   | GitHub Org `ecologic-tw` | 管理員 | 新增管理員後原管理員退出 |
   | Google 回饋表單＋回應試算表 | 建立者 Google 帳號 | 新增協作者 → 轉移擁有權；或改由專案共用帳號持有 |
   | 行為準則聯絡信箱 | 聯絡人 | 建議使用專案共用信箱，交接時變更密碼與復原資訊 |
   | 網址 | GitHub Pages | 不需移轉（綁 Org） |
3. **交棒檢查表**：新維護者能 `npm ci && npm run build`、能核准一個內容 PR、能存取表單回應、讀過指引，即完成交接。
4. **年度檢查**（併入 9 月角色檢視）：依賴、Node LTS、Actions 版本、外部連結有效性、表單擁有權。
